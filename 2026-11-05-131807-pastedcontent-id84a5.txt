    into errors. Only the repo-level errors (invalid URL, not found, rate limit)

    abort the run.
  ────────────────────────────────────────

  Takes: bundle

  Complexity formula (fix it before coding)

  Score = sum of 4 components, 25 points each, 0–100 total:
  - Size: 25 × min(1, log10(file_count) / 4), where 10,000 files gives the full
    25
  - Depth: 25 × min(1, max_depth / 10)
  - Large files: 25 × min(1, share_of_blobs_over_100KB / 0.10), where 10% or
    more large files gives the full 25
  - Language spread: 25 × min(1, (languages_with_≥1%_bytes − 1) / 5)

  Bands: under 25 = Low, 25–50 = Moderate, 50–75 = High, 75+ = Very high. The
  report prints each component's raw value and points. Say clearly that this 
  uses tree byte sizes, not lines of code, because counting lines would mean
  downloading every file.

  Dependency health definition (print it in the report)

  - Pinned: an exact version. That means == in pip, or a bare 1.2.3 in npm. ^,
    ~, >=, * or no version count as unpinned.
  - Up to date: the pinned version equals the registry's latest. For unpinned
    specs, show the latest version and mark the status "unknown (range)". Don't
    pretend to resolve ranges.
  - Healthy = ≥80% pinned and ≥80% of pinned deps up to date. Anything else is
    "Needs attention", with the reasons listed.
  - Compare versions with a simple numeric tuple. Anything that doesn't parse
    cleanly (pre-releases, -e, git URLs, -r includes, environment markers) is
    marked "unknown". Skip comments and blank lines.
